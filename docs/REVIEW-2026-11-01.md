## 1. 背景基线 A：WinUI 3 里与本项目直接相关的事实

WinUI 3 是 Windows App SDK 的一部分，与 OS 解耦发版；它构建的仍然是 Win32 桌面应用（可以是 unpackaged），只是 UI 层换成 XAML。对你的代码有实际影响的几条：

| # | 事实 | 对你的影响 |
|---|---|---|
| 1 | `Window` 不是 `FrameworkElement` | 已在 `MainWindow` 里踩到：`Window` 根不支持 `x:Bind`，`DataTemplate` 里也没有 `x:DataType`。**正解是抽一个 `UserControl` 承载内容**，这样 `x:Bind` 编回来的同时也能降内存（见 §7.1） |
| 2 | `{Binding}` 走反射、`{x:Bind}` 编译期生成 | 5000 行 × 4 个绑定，反射绑定是 204MB 里可优化的一块；`x:Bind` 通常省 30–60% 的绑定对象开销 |
| 3 | `ListView` 只有在默认 `ItemsStackPanel` 且不被 `ScrollViewer` 包裹时才虚拟化 | 你两条都满足了，这条没踩。但 `ListView.Header` 会跟着内容一起滚走，5000 项时表头很早就看不见（表头应移到 ListView 外面） |
| 4 | 大列表三种进阶手段：`x:Phase`、`ContainerContentChanging`、`ItemsRepeater` | 只读预览列表用 `ItemsRepeater` + `x:Phase` 可以明显压内存；`ListView` 的额外成本来自 ItemContainer 的选中/焦点状态机 |
| 5 | `AppWindow.Resize` 的参数是**物理像素**，不做 DPI 换算 | `AppWindow.Resize(new(1180,720))` 在 150% 缩放的屏上是 787×480 DIP，窗口看起来偏小。应按 `GetDpiForWindow(hwnd)/96.0` 乘一遍 |
| 6 | `MicaBackdrop` 只在 Win11 生效，Win10 静默降级 | 清单 `MinVersion=10.0.19041`，Win10 上会是没有背景色的纯色窗——可以接受，但别把 Mica 当必现效果写进验收 |
| 7 | 非打包 + `WindowsAppSDKSelfContained` 时没有 `Package.Current`，`resources.pri` 必须与 exe 同目录 | 已在 `EnsureResourcesPri` 里兜住，这条做对了 |
| 8 | WinUI 3 没有内建崩溃对话框 | 目前 `App` 没挂 `UnhandledException`，任何异常都是**进程静默消失**。这跟 P0-3 是同一个洞的两半 |

## 2. 背景基线 B：PowerRename 的实现方式（源码级）

PowerToys 里 PowerRename 的组成（`doc/devdocs/modules/powerrename.md` + 源码）：

| 组件 | 内容 |
|---|---|
| Shell 扩展 | `PowerRenameExt`：同时实现 `IShellExtInit`/`IContextMenu`（Win10 传统菜单）和 `IExplorerCommand`（Win11 一级菜单），**双注册**：传统注册 + 稀疏 MSIX 包 |
| UI | WinUI 3 应用（PowerToys **v0.59.0** 起从 WPF 迁到 WinUI 3，与你的技术栈一致） |
| 核心库 | `PowerRenameManager` / `PowerRenameItem` / `PowerRenameRegEx`（C++/WinRT + COM 接口 `IPowerRenameManager` 等） |

执行路径（`PowerRenameManager.cpp`，逐行看过）：

```cpp
#define FOF_DEFAULTFLAGS (FOF_ALLOWUNDO | FOFX_ADDUNDORECORD | FOFX_SHOWELEVATIONPROMPT | FOF_RENAMEONCOLLISION)
...
// 专用 STA 工作线程，进程启动时建一次，事件驱动
CoInitializeEx(nullptr, COINIT_APARTMENTTHREADED | COINIT_DISABLE_OLE1DDE);
CoCreateInstance(CLSID_FileOperation, ...);
// ★ 按深度从大到小入队：子项先改，父目录后改
spFileOp->RenameItem(spShellItem, newName, nullptr);
spFileOp->SetOperationFlags(FOF_DEFAULTFLAGS);
spFileOp->SetOwnerWindow(pwtd->hwndParent);     // ★ 你没有这一步
spFileOp->PerformOperations();
// 注释原文：不关心返回值，"宁可把控制权还给 explorer，让用户在失败时能干净地 undo"
```

四条值得你借鉴/纠偏的点：

1. **撤销走 Shell 的撤销栈，不是自己记账**。`FOFX_ADDUNDORECORD`（Win8 引入，官方文档原话：*"The file operation was user-invoked and should be placed on the undo stack. This flag is preferred to FOF_ALLOWUNDO."*）让资源管理器的 `Ctrl+Z` 能撤销这次批量改名。
   → **你 SPEC §0.3 第 8 条 `[判断]` 是错的**（"Explorer 的系统级 Ctrl+Z 无法撤销其它进程发起的批量重命名"）。跨进程完全可以：这个标志就是干这个的。PowerRename 的 Ctrl+Z 时好时坏（issue #19883）是另一回事，但机制存在。
   → 建议：**保留你的 WAL journal（跨重启、可审计，比 Shell 撤销栈强），同时加 `FOFX_ADDUNDORECORD` 作为免费的第二重保险**。两者不冲突，用户从资源管理器按 Ctrl+Z 也能救回来。
2. **冲突交给 Shell 自动编号**（`FOF_RENAMEONCOLLISION`），不是自己拦。你选了"默认红字阻止"，这是更保守的选择，没问题；但要知道 PowerRename 不会因为冲突失败。
3. **执行顺序按目录深度倒序入队**，PowerRename 支持递归，所以子项必须先于父目录改。你不做递归，但同目录下的**依赖顺序**问题依然存在（见 P0-1）。
4. **PowerRename 也不做逐项结果校验**——它把失败留给 Shell UI。你比它多做了校验，方向是对的，只是实现方式（事后按名字查）在链式改名时不可靠（见 P2-10）。

对比表：

| 维度 | PowerRename | 本项目 | 评价 |
|---|---|---|---|
| 菜单注册 | 双注册（传统 + 稀疏包） | 只做稀疏包 | M5 要补 Shift+右键兜底，PowerToys 是现成范本 |
| 进程拓扑 | Shell 扩展 + WinUI 3 UI + 核心库 | dllhost 壳 + WinUI 3 App | 你更薄，选得对 |
| 传参 | COM 接口 | stdin UTF-16 + `\0` | 你的更简单，`\0` 是唯一合法安全分隔符，正确 |
| 执行 | IFileOperation（单线程、深度倒序） | IFileOperation + CaseOnly 走两步 | 你的 CaseOnly 处理是 PowerRename 没有的加分项 |
| 撤销 | Shell 撤销栈 | 自建 WAL journal | 你的更强，但可叠加 `FOFX_ADDUNDORECORD` |
| 冲突 | Shell 自动编号 | 预览红字阻止 + 可选编号 | 取舍合理 |
| 逐项结果 | 无 | 事后按名字校验 | 思路对、实现待改（P2-10） |

## 2.5 追加实测（2026-11-01）：系统级 Ctrl+Z 到底怎么开

用户实测：改名 → 关闭程序 → 在资源管理器按 `Ctrl+Z`，没有任何反应。结论是**这不是 bug 而是架构事实**，同时**也确实能改成可用**。下面是四组端到端探针（真实 `IFileOperation` + 真实发键给资源管理器窗口）。

| # | 操作 | 结果 |
|---|---|---|
| 1 | `IFileOperation::RenameItem` 批改 2 项，flags **不带** undo | 执行成功；资源管理器 `Ctrl+Z` **无反应** |
| 2 | 同上，flags **加** `FOFX_ADDUNDORECORD (0x20000000)` | 执行成功；改名后再开一个资源管理器窗口到该目录，按 `Ctrl+Z` → **两项一起恢复原名** |
| 3 | `File.Move` 直接做仅大小写改名（文件） | **成功**（`case1.txt` → `CASE1.txt`，精确大小写校验通过） |
| 4 | `IFileOperation::RenameItem` 做仅大小写改名（文件 / **目录**） | **都成功**，目录里的子文件完好 |

四条推论：

1. **journal 永远不可能"系统级"**。资源管理器的撤销栈是 explorer.exe 进程内的 Shell 数据结构，没有公开 API 可以往里塞一条外部记录；唯一能让操作进入撤销栈的方式，就是**让 Shell 自己去执行它**——即 `IFileOperation`/`SHFileOperation` + `FOFX_ADDUNDORECORD`。你的 journal 是应用私有账本，程序一关就没人听了，所以 Ctrl+Z 必然无效。这不是"journal 做得不够好"，是两种机制各自的本体不同。
2. **你的代码明确排除了这个标志**：`FileOperationRunner.cs:106-111` 的注释写着"有意不加 `FOF_ALLOWUNDO`（撤销我们自己记）"。所以第 1 组实验就是你现在的行为。
3. **CaseOnly 项即使加了标志也救不回来**，因为它们走的是 `File.Move`（裸 Win32 改名，Shell 完全不知道）。而实验 3/4 说明**这套两步改名的前提是错的**：`File.Move` 和 `IFileOperation::RenameItem` 在 NTFS 上都能直接做仅大小写改名（文件、目录都行）。SPEC v1.2 #3 那次失败的真实原因是"在同一队列里引用尚不存在的临时名"，与大小写无关。
4. 实验 2 的时间顺序值得注意：**改名发生在先，资源管理器窗口是后开的**，`Ctrl+Z` 依然生效——撤销记录不依赖某个已存在的窗口/视图。

**建议的改法（推荐顺序）**

1. **删掉 `RenameCaseOnly` 整个分支**（`FileOperationRunner.cs:84-92`、`:156-179`），CaseOnly 项与普通项一起进 `IFileOperation` 队列。这样顺带解决 P1-4（文件夹改不了）和"两步走的中转名"问题。
2. `SetOperationFlags` 加 `FOFX_ADDUNDORECORD`（比 `FOF_ALLOWUNDO` 更被推荐，PowerRename 两个都加）。整批 = 一条撤销记录，`Ctrl+Z` 一次全回。
3. **journal 保留不动**。两者是互补的：
   - Shell 撤销栈：管"刚刚那一下反悔了"，跟进程死活无关，但重启 explorer / 注销就没了；
   - 你的 journal：管"昨天那批还能撤吗"，7 天、跨重启、可审计。
4. 注意一个新出现的一致性问题：用户可能在资源管理器里按了 `Ctrl+Z`，而你的 journal 仍是 `Applied`。点「撤销」时会发现 `to` 已不存在——你现有的逐项失效判定（`ExistsExact`）会把它记成"已失效"，行为是正确的，不用改；只是别把"journal 说 Applied"当成磁盘现状。
5. journal 驱动的反向执行**不要**加 `FOFX_ADDUNDORECORD`（否则资源管理器里又多一条"撤销的撤销"记录，用户按两次 Ctrl+Z 会看到文件在来回跳）。

## 3. P0：会丢数据 / 会让功能静默失效

### P0-1 批内交换/循环改名会被静默覆盖（数据丢失）

**证据**（探针 D，真实 `IFileOperation`）：

```
a.txt="AAA"  b.txt="BBB"   →  预览：两项都 Ok（无冲突）
执行后：Succeeded=1 Failed=1
        a.txt -> b.txt ok=False  改名后目标不存在
        b.txt -> a.txt ok=True
磁盘：a.txt='AAA'   b.txt=<缺失>          ← BBB 的内容永久消失
```

**根因**（两处叠加）：

1. `RenameEngine.MarkDiskConflicts`（`RenameEngine.cs:304-313`）把"本批会让出的源名"从占用集合里排除：

   ```csharp
   var vacating = ... group.Where(i => i.State is Ok or Warning).Select(i => i.OriginalName)
   if (vacating.Contains(item.NewName)) continue;      // 会被本批让出来 → 不算冲突
   ```

   对"链"（`a→b`、`b→c`）这是对的；对**环**（`a→b`、`b→a`）这是错的——`b.txt` 并不会"让出来"，它要变成 `a.txt`。

2. 执行器按列表顺序入队 + `FOF_NOCONFIRMATION`（`FileOperationRunner.cs:106-124`）→ Shell 遇到已存在的目标名**不提示直接替换**。

**建议（推荐）**：在 `MarkDiskConflicts` 之后加一轮**环检测**：同目录内建图 `OriginalName → NewName`（都用 `OrdinalIgnoreCase`），DFS 找环；环上的项标 `ConflictInBatch`，文案「批内循环改名」。

**备选**（更稳但更大）：不预判环，改为**全批两阶段**：先把所有项改成 `$br$<guid>` 临时名，再改成目标名。这样链、环、大小写全部一步到位，且天然规避"目标名被本批另一个项占用"的所有情况。代价是失败回滚要回滚两步（你有 journal，已经具备这个能力）。

**顺带**：`FOFX_ADDUNDORECORD` 加不加都不影响本条，但加了之后用户至少还能在资源管理器里 Ctrl+Z 抢救。

### P0-2 「上次操作可能未完成，是否回滚」的按钮永远失败

**证据**（探针 I，走的就是 `MainWindow.CheckPendingJournalAsync` 的代码路径）：

```
落盘 journal: 20261101-004533-….json state=Pending
Rejected=True  Reason=该批次未正常完成，请用「回滚未完成」  Undone=0
文件名当前: to存在=True from存在=False
```

**根因**：`UndoJournal.IsUndoable`（`UndoJournal.cs:128-132`）明确拒绝 `Pending`，理由文案是「请用「回滚未完成」」；而「回滚未完成」这个入口**并不存在**——`CheckPendingJournalAsync`（`MainWindow.xaml.cs:457-462`）点的 Primary 按钮调用的正是 `pending.UndoAsync()`，于是必然走到拒绝分支。

**额外讽刺**：`BatchRename.ShellTest/Program.cs:460-461`（第 15 组）断言的正是"Pending 拒绝撤销"，这条断言把 bug 固化成了"预期行为"。

**建议**：

```csharp
// UndoJournal 里给恢复路径一个独立的入口，不从 IsUndoable 的公共闸门走
public async Task<UndoOutcome> RollbackPendingAsync(CancellationToken ct = default)
{
    if (State != JournalState.Pending) return new UndoOutcome { RejectReason = "不是未完成批次" };
    return await UndoCoreAsync(ct);   // UndoAsync 去掉状态闸门后的主体
}
```

同时在 ShellTest 里把第 15 组改成「Pending → RollbackPendingAsync 成功回滚、状态变 Undone」，并把 `UndoAsync(Pending) → 拒绝` 保留为另一条断言。

### P0-3 执行路径是 `async void` 且无 try/catch

**位置**：`MainWindow.xaml.cs:300`（`OnExecute`）、`:393`（`OnUndo`）。

```csharp
private async void OnExecute(object sender, RoutedEventArgs e)
{
    ...
    journal.Save();               // write-ahead：此处已落盘 Pending
    var result = await runner.RunAsync(targets);   // ← 任何异常都从这里逃出去
```

任何一处抛出（COM 调用失败、`SHCreateItemFromParsingName` 对失效路径 `ThrowOnFailure`、磁盘掉线、`journal.Save()` 第二次写失败）都会：

1. 从 `async void` 冒到 `DispatcherQueue` → **WinUI 3 直接终止进程，无对话框、无日志**（`App` 没挂 `UnhandledException`）；
2. journal 永远停在 `Pending` → 下次启动弹出「上次操作可能未完成」，然后撞上 P0-2 的按钮失效 → 用户被卡在一个假警报里。

**建议**：

- `OnExecute`/`OnUndo` 整体包 `try/catch`，`catch` 里：`journal` 已有的结果照常回写（至少写 `Applied` + 已知项），失败写日志 + `SetError`；
- 给 journal 加 `Aborted` 状态（或 `Pending` + `Error` 字段），崩溃恢复对话框按「已知 ok 项」回滚，不要依赖"全部成功"；
- `App` 构造函数里挂三个兜底：`UnhandledException`、`AppDomain.CurrentDomain.UnhandledException`、`TaskScheduler.UnobservedTaskException`，全部写 `%LOCALAPPDATA%\BatchRename\logs\app.log`。**目前 App 进程一行日志都没有**，M3 的问题全靠肉眼复现，这本身是个隐患。

## 4. P1：功能缺陷

### P1-4 仅大小写改名的**文件夹**必然失败

**证据**（探针 C）：

```
lowerdir → LOWERDIR   State=Ok CaseOnly=True
Succeeded=0 Failed=1 err=改名失败：Could not find file '…\lowerdir'.
目录仍然存在(原名)=True   子文件是否还在=True     （数据没坏，但功能不可用）
```

`File.Move` 只动文件；`.NET` 的实现会在目录上抛 `FileNotFoundException`。

**修法**（推荐，已实测）：`FileOperationRunner.cs` 里 `IFileOperation::RenameItem` 对**文件**和**目录**的仅大小写改名都直接成功（§2.5 实验 4），所以 `RenameCaseOnly` 这个两步分支可以**整体删掉**，CaseOnly 项跟普通项一起进队列。当年 v1.2 #3 那次 `0x80070002` 的病因是"在同一队列里引用还没生成的临时名"，跟大小写无关。

如果因为别的原因要保留两步，则两跳都必须区分目录：

```csharp
if (Directory.Exists(item.FullPath)) Directory.Move(temp, target);
else File.Move(temp, target);
```

### P1-5 改扩展名 + 自动编号 → 编号位置错、扩展名回退

**证据**（探针 B）：

```
a.txt 与 a.md 同目录，规则：仅扩展名 txt→md，开自动编号
实际：a.txt -> "a.md (1).txt"   （期望 "a (1).md"）
```

**根因**（`RenameEngine.cs:375-383`）：`item.Ext` 是**改名前**的扩展名，`item.NewName` 在 ExtOnly 场景下不以它结尾，于是 `stem` 退化成整个 `NewName`，再拼回旧 `ext`：

```csharp
var stem = ext.Length > 0 && item.NewName.EndsWith(ext, ...) ? item.NewName[..^ext.Length] : item.NewName;
```

**修法**：不要从字符串反推，直接从目标名切分：

```csharp
var (stem, extOfNew) = NameSplitter.Split(item.NewName, item.IsDirectory);
var candidate = n == 0 ? item.NewName : $"{stem} ({n}){extOfNew}";
```

这也是个提醒：**同一份"主名/扩展名切分"逻辑在两个地方各写了一遍**（`NameSplitter` 一处、这里反推一处），是典型的重复实现腐化点。

### P1-6 撤销部分失败也写 `Undone` → 这一批再也撤不回来

`UndoJournal.cs:202-203` 无条件 `State = Undone; Save();`，即使 `result.Failed > 0` 或 `invalid > 0`。

后果：用户看到「已撤销 96 项，3 项失败」，想再试一次 → `IsUndoable` 直接拒绝「该批次已撤销过」。而且 `Entries[i].Ok` 也没按回滚结果更新，失败项在 journal 里仍是"改成功过"，信息永久丢失。

**建议**：撤销后按结果回写一个新的 `UndoState`（比如 `PartialUndone`），`IsUndoable` 允许对 `PartialUndone` 再撤一次（幂等：已回滚的项 `From` 存在、`To` 不存在 → 自然被跳过）。

### P1-7 执行后 `IsRenamed` 没有复位入口

`RenameEngine.Run`（`RenameEngine.cs:109-116`）对 `IsRenamed` 项直接 `continue`，永远返回 `State=Renamed`。而 `IsRenamed` 只在 `RemapItems` 里被置 `true`（撤销时置 `false`）。

结果：**执行完一批之后，在同一窗口里再也改不动它们**（改查找词、改大小写都没有预览变化），只能撤销或关窗重开。这也是 `OnExecute` 末尾要把查找/替换框清空的原因——但清空只是掩盖了症状。

**建议**（推荐）：执行成功后把 `IsRenamed` 项从"本批"里摘出去（保留行以显示结果），并给底栏一个「继续改名这批」的复位按钮；或更简单——执行成功后按新路径重新 `CreateItems` 一遍，只把结果文案保留在底栏（`_resultMessage` 机制已经能做到）。

### P1-8 journal 跨重启不可撤销 + 第二个 verb 未实现

`_lastJournal` 只在 `OnExecute` 里赋值（`MainWindow.xaml.cs:350`），撤销按钮靠 `_lastJournal is { State: Applied }` 使能。所以：

- 关窗再打开 → 上一次的 journal 明明还在磁盘上（7 天内有效），但 UI **没有任何入口**能撤它；
- SPEC §1.3 说的「右键菜单第二个 verb『撤销上次重命名』」也没做。

**建议**（按成本排序）：① 启动时 `UndoJournal.LoadAll().FirstOrDefault(Applied)` 挂到 `_lastJournal`，零成本；② 底栏加一个「最近批次」下拉（最多 20 条，`RuleSummary` 已经有现成的一句话摘要，正是为这个准备的）；③ 第二个 verb 走同一个 App，参数用 `--undo-last`，Shell 侧只是多一个 `IExplorerCommand` 实现（`GetState` 判断有没有可撤的 journal，这需要一次文件存在性检查——注意别把它放进 `GetState` 的慢路径）。

## 5. P2：正确性 / 健壮性

### P2-9 执行前不刷新引擎（150ms 防抖窗口内的旧规则）

`OnExecute` 直接用 `_items` 当前的 `NewName/State`，而它们在最后一次输入后要等 150ms 防抖才更新。用户打完字立刻点「执行」（或按 Enter，`OnRootKeyDown` 同样不等）→ 用的是**上一次**规则算出来的名字。

**修法**：`OnExecute` 开头 `_debounce.Stop(); RefreshPreview();` 再收集 targets。一行的事。

### P2-10 结果校验是 O(n²)，且对链式改名会误报

`FileOperationRunner.cs:133-142` 对每个项调 `RenameEngine.ExistsExact`，而 `ExistsExact` 每次都要**整目录枚举**（`RenameEngine.cs:45-46`）。

**实测**（探针 E）：目录 4000 个文件，单次 `ExistsExact` = **0.735ms** → 4000 项改名后逐项校验 ≈ **2.9s**；撤销路径每项调两次（`e.To`、`e.From`），≈ **5.9s** 纯校验开销。你 SPEC §8.11 的目标是"执行 5000 项 2–5s"，光校验就吃掉一半。

第二个问题更隐蔽：**链式改名时它会误报**。探针 D 里 `a→b` 明明成功了，但因为 `b.txt` 随后被 `b→a` 挪走，校验时 `b.txt` 不存在 → 报「改名后目标不存在」。也就是说"目标名存在"不等于"这一步成功了"。

**建议（推荐）**：实现 `IFileOperationProgressSink::PostRenameItem`，拿 Shell 给的逐项 `HRESULT`。这同时解决三件事：真实成败、错误码翻译（`ERROR_ACCESS_DENIED` → 权限不足/被占用）、以及省掉 2.9s。CsWin32 会生成接口，你当年担心的 15 个回调里其余的大多返回 `S_OK` 即可。

**备选（更小的改动）**：`ExistsExact` 改成"按目录建缓存"——一次 `EnumerateFileSystemEntries` 建 `HashSet<string Ordinal>`，后续查询 O(1)。改十来行，省掉 99% 的开销，但误报问题仍在。

### P2-11 没调 `SetOwnerWindow`

`FileOperationRunner.cs:106-124` 只设了 flags。缺 `op.SetOwnerWindow(mainWindowHwnd)` 的后果：

- `FOFX_SHOWELEVATIONPROMPT` 触发的 UAC 对话框没有 owner，可能弹在窗口后面/任务栏闪烁；
- Shell 自己的错误 UI（万一）也是孤立窗口。

PowerRename 是显式调了的（`SetOwnerWindow(pwtd->hwndParent)`）。修法：`MainWindow` 把 `WindowNative.GetWindowHandle(this)` 传进 `RunAsync`，`RunAsync(items, hwnd, ct)`。

### P2-12 单实例管道循环没有退避

`SingleInstanceGate.cs:75-106`：`while(true)` 里 `new NamedPipeServerStream(...)` 失败 → `catch` → `continue`。若构造持续失败（管道名被占、权限问题），这是一个**不带 sleep 的死循环**，后台线程 100% 吃一个核，且不会有任何提示。

**修法**：`catch` 里 `await Task.Delay(500)`，连续失败 N 次后退出循环并写日志（此时单实例退化，功能仍可用）。

顺带：管道默认 DACL 只允许同用户/同 IL 连接，够用；如果想更严，`NamedPipeServerStream` 的 `PipeSecurity` 显式拒绝 `Network`。

### P2-13 `Install-Sparse.ps1` 在 Windows PowerShell 5.1 下必挂

**证据**（真实执行）：

```
parse errors: 0
xml-parse FAILED: 无法将值"<?xml version="1.0" encoding="utf-8"?>…"转换为类型"System.Xml.XmlDocument"
  其中 <DisplayName>鎵归噺閲嶅懡鍚?/DisplayName>   ← 被当作 GBK 解码，吃掉了右引号
```

`tools/Install-Sparse.ps1:28` 是 `[xml]$manifest = Get-Content $manifestPath -Raw`，而 `AppxManifest.xml` 是**无 BOM 的 UTF-8**。Windows PowerShell 5.1 的 `Get-Content` 默认按 ANSI（本机 GBK）解码 → `[xml]` 转换失败 → `$ErrorActionPreference='Stop'` → 脚本在第 28 行直接中止。

而 `docs/SPEC.md` 的 v1.1 补记里**已经写明这条**（"`Get-Content -Raw` 必须加 `-Encoding UTF8`"），只是没落到脚本里。你当时能装上，多半是在 pwsh 7 里跑的（它默认 UTF-8），或者清单当时带 BOM。

**修法**（三选一，推荐 ①）：

```powershell
# ① 显式编码（最小改动，脚本仍是 ASCII + 中文注释也无所谓）
[xml]$manifest = Get-Content $manifestPath -Raw -Encoding UTF8
# ② 用 XML API 自己读，完全绕开编码问题
[xml]$manifest = [xml](Get-Content $manifestPath -Raw -Encoding UTF8)
```

顺手建议：所有 `.ps1` 存成 **UTF-8 with BOM**，或注释保持纯 ASCII（PowerShell 5.1 对无 BOM 脚本按 ANSI 解码，中文注释有可能吃掉下一行——这是本机的老坑）。

### P2-14 `active.pid` 永不清理

`SingleInstanceGate.Dispose()`（`SingleInstanceGate.cs:143-157`）负责删 pid 文件和释放 mutex，但**全工程没有任何地方调用它**（`Environment.Exit(0)` 不触发 `Dispose`）。留下一个永久残留的 `active.pid`。

目前不致命（下一个实例抢到 mutex 后会覆盖它），但这是个"看起来有清理、实际没有"的假安全感。修法：挂 `_window.Closed += (_,_) => _gate?.Dispose();`，或干脆在 `StartServer` 里用 `FileOptions.DeleteOnClose` 思路改成"进程存活即锁"。

### P2-15 批内冲突 key 与磁盘检查的比较器不一致

`MarkBatchConflicts`（`:251`）用 `Dictionary<(string,string), …>` 默认比较器 = **Ordinal 大小写敏感**；`MarkDiskConflicts`（`:287-296`）用 `OrdinalIgnoreCase`。

后果：同一目录下若两项的新名只差大小写（`Same.txt` / `same.txt`），批内互撞检测不到，磁盘检查也查不到（这两个名字都还不在磁盘上），但 NTFS 上它们是同一个名字 → 执行时第二个把第一个覆盖。

现实中用一条全局规则很难造出这种组合（所以这条是 P2 而不是 P0），但只要以后加"按列表项分别设置规则"或"随机/日期填充"，它立刻变成 P0。修法：批内 key 统一 `OrdinalIgnoreCase`（与卷属性对齐的那套比较器，`ConflictKey.Comparer` 本来就是 SPEC 里设计过的）。

### P2-16 UI 层的两个小坑

**① 状态色硬编码、不跟随主题**（`StateToBrushConverter.cs:11-15`）：`#E86A6A` / `#84C884` 这类值在深色主题下还行，浅色主题下绿/黄对比度不足，而且运行中切换主题不会重算（`SolidColorBrush` 静态实例）。

建议：改用主题资源 `SystemFillColorCriticalBrush` / `SystemFillColorCautionBrush` / `TextFillColorSecondaryBrush` / `SystemFillColorSuccessBrush`（`Application.Current.Resources` 里取），或在双主题下各给一套。

**② `AppWindow.Resize(1180,720)` 用的是物理像素**：150% 缩放下实际只有 787×480 DIP。修法：

```csharp
var hwnd = WinRT.Interop.WindowNative.GetWindowHandle(this);
var scale = PInvoke.GetDpiForWindow((HWND)hwnd) / 96.0;
AppWindow.Resize(new SizeInt32((int)(1180 * scale), (int)(720 * scale)));
```

**③ 表头会滚走**：`ListView.Header` 跟着内容滚，5000 项时列头早就没影了。把表头 `Grid` 移出 `ListView`，放在它上方的 `Grid.Row` 里（列宽用同样的像素+星号比例）。

## 7. 优化建议（按收益排序）

### 7.1 内存：204MB → 目标 <150MB

现在是「空窗 110MB + 5000 项 94MB」。94MB 里主要是 5000 个 `RenameItem` + 5000 个 `{Binding}` 反射绑定 + 5000 个行容器。

三条按收益排序：

1. **抽 `UserControl` 承载窗口内容**（`Window` 只放一个 `RenameView`），`DataTemplate` 加 `x:DataType="models:RenameItem"`，绑定改 `x:Bind`。这是 SPEC §7.4.1 已经写过的方案，也是唯一能同时降内存和提滚动的改动。
2. **行模板减负**：每行现在是 1 `Grid` + 1 `CheckBox` + 3 `TextBlock` + 1 `FontIcon`。`FontIcon` 那列（箭头）可以用 `TextBlock Text="→"` 替代，少一个 `IconElement` 子对象。
3. **`ListView` 换 `ItemsRepeater` + `x:Phase`**（如果不需要多选/焦点语义）。你用的是 `SelectionMode=Single` + `Space` 切勾选，其实只需要"当前行"这一个状态，`ItemsRepeater` 够用，省掉 ItemContainer 的状态机。

顺带：`RenameItem` 现在给 `NewFullPath` 每次 getter 都 `Path.Combine`，两个地方绑它（列 + 校验）→ 5000 项 × 每次刷新。改成 `NewName` 变化时算一次缓存即可（`_newFullPath` 字段）。

### 7.2 预览刷新：两层防抖（SPEC §8.11 写了、代码没做）

`RefreshPreview` 在 UI 线程同步跑，而且 `RenameEngine.Run` 内含**整目录枚举**（`MarkDiskConflicts`）。本机 SSD 上 2000 项 4.9ms 无所谓，但：

- 输入框每敲一个字 → 150ms 后枚举一遍所有涉及目录；
- 网络盘 / 机械盘 / 目录里 5 万个文件时，这个开销是秒级，直接卡 UI。

建议按 SPEC 原设计做第二档：150ms 内只跑"文本规则 + 批内互撞"（纯内存），停手 400ms 后再跑磁盘冲突；磁盘结果用 `_diskConflicts` 缓存参与最终 `State` 计算。或者更省事：把 `MarkDiskConflicts` 的目录枚举结果按 `(dir, lastWriteTime)` 缓存几秒。

### 7.3 结构：把 `ConflictResolver` 真抽出来

`RenameEngine.cs` 现在 398 行，混了四件事：编排、文本规则调用、九条校验、两种冲突策略 + 自动编号。SPEC §4.2 早就规划了 `Core/ConflictResolver.cs`。

抽出去的好处很实际：冲突检测是**唯一需要碰磁盘**的部分，单独成类之后才能做上面 7.2 的两层防抖（"纯引擎"那份不碰磁盘，可以放心在 UI 线程跑），也才能给 `IFileSystem` 留注入点、把冲突逻辑写进单元测试而不需要真建目录。

### 7.4 日志

目前只有 Shell 侧有 `shell.log`。App 侧零日志，M3 的三个真实故障（覆盖、`0x80070002`、`File.Exists`）全靠肉眼复现。建议加一个 200 行的 `Log.cs`（和 Shell 侧同构，1MB 循环），至少打这几条：

- 启动：参数条数、解析耗时、首帧耗时；
- 执行：`journal.Id`、targets 数、`PerformOperations` 的 `HRESULT`、逐项结果；
- 撤销：`journal.Id`、逐项失效原因；
- 未处理异常（三个兜底钩子）。

无常驻、低频的工具，日志的价值就是把"用户说'它没反应'"从猜测变成一行时间戳。

### 7.5 键盘与交互补齐

- `Esc` 有未执行改动时的二次确认（README 已记为已知限制，`ContentDialog` 20 行）；
- `Ctrl+A` / `Space` 改完勾选后同步 `SelectAllBox.IsChecked`（现在会不一致：全选后复选框还是旧状态）；
- 执行中禁用规则输入区（现在 `_busy` 只挡了刷新，控件仍可改，改完的规则会在下一次刷新时突然生效）；
- 底栏「全选」目前是 `CheckBox` 且默认勾选，但 `Ctrl+A` 不会改它 → 三态语义混乱，建议改成 ToggleButton 或用 `IsThreeState`。

### 7.6 journal 的去留（2026-11-01 追加决策分析）

**现状实测**（`%LOCALAPPDATA%\BatchRename\journal`）：20 个文件、共 85KB、132 条 entry、平均每批 6.6 条、单文件最大 3.2KB、状态分布 10 Applied / 10 Undone / 0 Pending。

`schema=1` 的这本账现在同时承担四件事，必须分开评估：

| 职能 | journal 是唯一提供者吗 | 结论 |
|---|---|---|
| ① 撤销「刚刚那一下」 | **不是**了。加 `FOFX_ADDUNDORECORD` 后资源管理器 `Ctrl+Z` 就能撤（§2.5 实测），且与进程死活无关 | 让给 Shell |
| ② 撤销「上次/前几天那批」 | 是。但无常驻 + 关窗即退 ⇒ 用户要撤销必须先重新打开工具；而此刻 Explorer 的 Ctrl+Z 通常还在。需求强度低 | 砍掉历史，只留最近 1 条 |
| ③ 崩溃中途的 write-ahead 标记 | **是**（唯一不可替代的职能）。没有它就无法区分「改完了」和「改了一半」 | **保留** |
| ④ 部分失败的逐项 `ok` 记录 | 是。但 UI 至今没有失败清单对话框（README 已列为已知限制），价值尚未落地 | 保留（成本近零） |

三个方案：

| 方案 | 内容 | 代价 | 收益 |
|---|---|---|---|

- 删：`MaxUndoAge`、`Prune`、`LoadAll`（保留一个 `LoadLast()`）、`Create` 里的时间戳 `Id`；

- 挪：`RuleSummary` 只在单文件方案里没用（没有列表可展示），建议并进 App 日志而不是 journal；
